44. Access Control List (ACL)
=============================

Let's assume we have three consumers and two services behind Kong. We already secured alpha and beta with the API key plugin; all three consumers have valid API keys. In this condition, all consumers can access alpha and beta. But we need to implement these rules. Alpha can only be accessed by the consumer, which is the partner, represented with human icons on this slide. Beta can only be accessed by consumers, which is internal, represented with a computer icon.

Kong can help us to do this.

We need to combine authentication, which exists on alpha and beta, with an access control list or ACL plugin. The mandatory requirement here is that we have to put an authentication plugin to services. We want to add an ACL plugin so that Kong can recognize the consumer based on authorization (in this example, API key)

With the ACL plugin, we can create a "partner" group and add Partner 1 and Partner 2. Then, we create an "internal" group and add an internal one. Then, in alpha, we only allow the "partner" group to access it using the allowlist feature. In beta, we allow the "internal" group to access it. ACL plugins provide allowlist and denylist rules.

Scenario presented on Access-control-list-scenario.png

ACL plugins provide allowlist and denylist rules. In allowlist, we allow access from certain consumer groups and reject everything else. So if we put group blue as allowlist, only consumers in that group can access API, while the others are blocked. - Access-control-allow-list.png

Conversely, if we deny one consumer group, only that group that cannot access service, the others are allowed. So if we denylist group blue, only consumers in that group cannot access API, while the others are allowed. - Access-control-denylist.png

45. Rate Limiting
=================

Rate limiting controls the amount of incoming traffic to API behind Kong. In other words, it limits how many HTTP requests a developer can make in a given period. Kong period can be seconds, minutes, hours, days, months, or years.

For example, let's say we configure the limit to omega and allow five requests/minute. Assume consumer 1 sends a request every 1 second. So, Consumer 1 already requests five times within 5 seconds, and at the 6th request, it will get HTTP status 429 (too many requests), and Kong does not forward the request to omega.

Thus, omega traffic is not full and can still serve requests from other consumers. Rate limiting is commonly used to allow better data flow and increase security by mitigating attacks such as Denial of Service.



Configure Onemga Service to 5 requests per minute
-------------------------------------------------

Go to http://localhost:8002/plugins / + New Plugin / Rate Limiting
	- minute: 5
	- Install

We will use default values for other parameters. Note that for policy, there is a "redis" policy. We must install a Redis server if we want to use this policy.

For more information on parameters, we can read in Kong Manager or go to the Kong hub documentation page.


Test the rate limiting with Postman
-----------------------------------
Use Postman / Course Content / REST API Services / Omega / GET Omega - Fast Response

Send the request 5 times. On the 6th time we will receive response with status code 429 Too Many Requests





46. Request Size Limiting
=========================

Some APIs might accept a large request body for example, an API to upload file. In such a case, we want to restrict the file size consumers submit to avoid burdening our API. So we can put a request size limit on Kong.

Request size means the total size of the payload, like JSON and file, if any. Any request with a total size greater than allowed will be rejected. - request-size-limit.png


Configure request size plugin
-----------------------------
Go to Kong Manager http://localhost:8002/plugins / + New Plugin / Request Size Limiting
	- allowed_payload_size: 2			# 2 mb
	- Install


Test the request size limiting with Postman
-------------------------------------------
Test 1:
Use Postman / Course Content / REST API Services / Beta / POST - Beta Calcualte MD5

	- Value: + New file from local machine, choose small file below 2 mb

When we send the request it will return response with status code 200 OK and empty hash of the file.


Test 2:
Use Postman / Course Content / REST API Services / Beta / POST - Beta Calcualte MD5 
In body tab add
	- Key: f
	- Value: + New file from local machine, choose small file over 2 mb

When we send the request it will return response with status code 413 Request Entity Too Large and error message.

Delete the request size limiter for the next lections.





47. Request Termination
=======================

This plugin terminates incoming requests with a specified status code and message. This plugin allows us to stop traffic on a Service or a Route or even block a particular Kong Consumer. 


CASE 1
------
A sample use case for this is when alpha service is temporarily unavailable. We can set the request termination plugin on alpha, and Kong sends HTTP status 503 (Service Unavailable) with a custom error message and does not proxy the request.


Configure Request Termination Plugin on Alpha service
-----------------------------------------------------
Go to Kong Manager http://localhost:8002/services / Alpha / Plugins / + New Plugin / Request Termination
	- message: Sorry, this service is under maintenance
	- Install

For more information on parameters, we can read in Kong or go to the Kong plugin documentation page.

CASE 2
------
Another use case is to block consumers temporarily. 

Suppose that we have three consumers. All have access to the alpha service. At some point, the "Consumer 3 "account is hacked, and the hacker sends many abnormal requests to Kong. We can then set the request termination plugin to consumer 3, so only request from consumer three account are terminated. 48. Proxy Cache
===============

Sometimes, we have an API frequently used with the same data. For example, take an API to calculate interest rates based on a particular amount and loan period. Such API might take a moment to do heavy calculations.

Still, as long as the business calculation formula remains the same the result for calling API will be consistent for the same amount and loan period. If such a calculation took 5 seconds, then every API call will need at least 5 seconds to retrieve data.

We can use a cache for such an API to speed up API performance. Cache allows us to reuse previously retrieved or computed data efficiently.

On the first hit of API, we need 5 seconds. Then, we put the result of the calculation in the cache. We can retrieve data from the cache for the next calls to API with the same amount and loan period. This way, the next calls will take less than 5 seconds, and there will be no computation so that no processing power will be used. Cache usually takes place in memory, so the cache size is limited. Usually, we cache items for a particular time or until the cache itself is full so we need to delete old cache data for newer data to take place.

We can put the cache in many places, from the API consumer, the first node in the API call chain up to the backend itself, the last node in the call chain, up to the backend itself, the last node in the call chain. The closer we put the cache to the consumer, the more performance we will gain.

It usually makes sense to put a cache on the API gateway. API gateway like Kong usually offers caching features. Of course, depending on the requirement, we can also put cache on multiple nodes. - cache-patterns.png
