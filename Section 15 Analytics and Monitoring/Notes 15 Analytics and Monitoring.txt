52. Distributed Tracing
=======================


In a microservice architecture, business logic can call a single API or combine several APIs to process one logic. Each of the APIs can be in a different application or even a different server. So, latency data can be an issue.

It is a good idea to have data regarding execution time so we can troubleshoot latency problems in microservice architecture. But it is not only about timing. 

In monolith architecture, debugging and reproducing the error is relatively easy since all logic is in one place if something goes wrong. 

The diagram on picure distributed-tracking.png, which calls logic at microservice architecture. The logic can be scattered among multiple APIs. And we can also have asynchronous calls. So we need to know the call chain and which API has a problem or returning an error. We can track requests with distributed tracing as they go through multiple services. We can track timing and other metadata for each API call and this information can be reassembled to provide a complete picture of the application's behavior at runtime. We can trace either synchronous or asynchronous calls.

Every call to chain API, consists of 4 calls on four distributed services. Three synchronous calls and one asynchronous. All four build up the chain API, so we must trace them all. - simple-distributed-tracing-diagram.png



Zipkin
------

One popular distributed tracing tool is Zipkin. It's free and capable of visualizing API call chains like the previous diagram. Kong provides a Zipkin integration plugin. The Kong plugin can trace each request using the Zipkin. However, our services must be configured for Zipkin instrumentation to create a chain call like the previous slide. To create this instrumentation, please go to Zipkin's official website about instrumentation and find documentation for each programming language. - https://zipkin.io/pages/tracers_instrumentation.html

We must have Zipkin running, so we will run one using the docker. At this point, we should already extract docker.zip from the last section of the course from a lecture with the title "Resources & References" and has subfolder “zipkin”. From terminal, go to that subfolder and run the docker compose.

Go to Kong Manager Plugin Page http://localhost:8002/plugins / + New Plugin / Zipkin

	# In production, where our application is already stable, it is better to lower this value to 0.1 - 10% of sample request.

53. UDP Log + Elastic Stack For Analytics
=========================================

Analytics is an important part of measuring and improving our service. In this course, we will learn how to know several things and create graphical representations of data like API usage frequency shows API that is used often or seldom. API performance, to know which endpoint is slow and needs improvement. Also, the API error rate is based on the HTTP status response. 

This course will use Kong and Elastic stack to do analytics. There are many products of Elastic stack, where we will use Elasticsearch, Logstash, and Kibana for analytics. For data storage, we will use Elastic Search. It is a free, open-source search and analytics engine. Elastic search saves data in JSON format, and data creation or manipulation can be done using REST API. Even selecting data in Elasticsearch can be done using the REST API. Elastic search is optimized for search engines and can find data fast. Elastic search can be scaled horizontally, making it possible to work with much data.

To collect and send data to Elasticsearch, we will use Logstash. Logstash has way more capability than just sending data to Elasticsearch. It can ingest data from multiple inputs, like a relational database or file system, from a real-time messaging system like RabbitMQ, Apache Kafka, and many more. Logstash has a wide variety of output for the output: console, files, database, and even big data stack. Logstash can parse and transform data on the fly, not just send raw data. So, the input system does not need to change how it stores data, but output systems can get data format as required, using logstash as an intermediary.

To visualize data in a readable format, we use Kibana. Kibana will take data from Elasticsearch, and we can create various charts from it. We can also do queries, filter the data specific to our needs, and visualize the data in time series. We can even create a real-time dashboard using Kibana. The elastic stack is powerful and comes with a free edition. 

But wait, what about Kong?

Well, we will gather data from the Kong log.

Kong can provide system logs. It's now up to us to enable the log and process it. So, we will put a UDP plugin in Kong to send log data into logstash so we can visualize them using Elasticsearch and Kibana. - analytics-stack-ELK.png

Working with elastic stack technology: Elasticsearch, kibana, and logstash require complex setup. In the video, I already configured the elastic stack so we can focus on Kong.

56. Kong Metrics With Prometheus & Grafana
==========================================

Kong provides useful metrics and charts about the health and performance of Kong nodes as well as metrics about the usage of API behind Kong We can see those metrics, by using kong plugin, combined with prometheus and grafana.

Prometheus is an open-source systems monitoring and alerting toolkit. It store time-series data. Monitoring tools built around time series data need to do the following within high transaction volume: 
	- Collect events with timestamp Store those events
	- Queries of these events

Offer graphical monitoring of these events so that trends can be followed over time.

Prometheus collects metrics from upstream servers by scraping metrics from HTTP endpoints on that server. In this case, the server is kong node and metrics generated by plugin.

Grafana is a visualization tools. It can get data from various datasource and display those data as real-time charts.

It is not mandatory to have both Prometheus and grafana. Each is independent tool. In fact, grafana can get data from many sources other than prometheus. But Kong already provides official grafana dashboard that we can use to display Kong metrics so we can monitor kong node in no time.

Both prometheus and grafana has docker image, so we can start fast. To monitor kong, we must have prometheus and grafana, so we will run them using docker.
